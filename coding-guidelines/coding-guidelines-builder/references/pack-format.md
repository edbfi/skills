# Pack format

The builder's output is a **guidelines library**: plain Markdown and JSON that coding agents read
when pointed at it. It is never a skill. It contains no `SKILL.md` and is never written into a
skill-discovery directory (`.agents/skills/`, `.claude/skills/`, `.codex/skills/`).
`packs.py check` enforces everything on this page that a script can see.

## Contents

- Library root
- Version resolution
- Component pack
- Stack pack
- `pack.json`
- Rules for every file

## Library root

```text
<library-root>/
  INDEX.md               # generated by `packs.py index`; never edited by hand
  components/<pack-id>/  # one pack per component and version line
  stacks/<pack-id>/      # one pack per combination of components
```

The same relative layout is used wherever a library lives (a builder output folder, a shared
guidelines repository, a consumer's `.agents/guidelines/`), so relative links keep working when
packs are copied. A single-component request produces one component pack. A multi-part request
produces a component pack per component plus one stack pack. Component packs are stack-agnostic;
anything specific to a combination lives in the stack pack.

## Version resolution

| Request | Effective constraint | Resolves to | Pack id |
|---|---|---|---|
| `TypeScript` | none | newest stable overall | `typescript` |
| `TypeScript 6` | `6` | newest stable 6.x | `typescript-6` |
| `TypeScript 6.0` | `6.0` | newest stable 6.0.x | `typescript-6_0` |
| `TypeScript 6.0.3` | `6.0.3` | exactly 6.0.3 | `typescript-6_0_3` |
| `Python 3.14` | `3.14` | newest stable 3.14.x | `python-3_14` |
| `Drizzle 1.0 RC` | `1.0-rc` | the `rc` dist-tag in 1.0, else the newest unsuffixed 1.0 rc | `drizzle-orm-1_0-rc` |

1. **Stable** means no prerelease marker (alpha, beta, rc, pre, preview, canary, next, nightly,
   dev, snapshot, insiders, milestone). Prereleases are used only when the request names one.
   Builds with a commit or date suffix (`1.0.0-rc.5-5935859`) are used only when named exactly.
2. **Three separate facts.** Toolchain or package version, language mode or edition (Swift 6 mode,
   Rust 2024 edition) and targets (minimum OS, runtime or browser, such as iOS 18) are independent.
   A newer toolchain never raises a target. All three are recorded in `pack.json`.
3. **Compatibility narrowing.** `registry_versions.py` reports each resolved version's declared
   peer, engine and interpreter ranges. For an unqualified or loose request, pick the newest version
   inside every range the other components declare, optional peers included, and record the
   narrowing (`constraint_source: "compat"`, `narrowed_by`). For a version the user named that falls
   outside a range: a required peer or engine range makes the stack unsatisfiable (stop and report);
   an optional peer range is advisory (proceed, record "outside declared peer range" in the stack's
   `versions.md`, and let the examples prove it works).
4. **Pack ids** are `<slug>[-<effective constraint>]` with `.` written as `_`. The slug is the
   project's official name, lowercased and hyphenated (`panda-css`, `ark-ui`, `drizzle-orm`). Reuse
   is decided by `(registry, package, effective constraint, targets)`, never by the slug.
5. **Identity follows the effective constraint.** A compat-narrowed pack is
   `typescript-6` with request `TypeScript 6`, so refreshing it alone stays on 6. A stack records
   each dependency edge with the original request, the effective constraint and the reason; when a
   stack refresh moves an edge (a later framework peers `^7`), the stack points at `typescript-7`
   and the old pack stays until someone removes it.
6. **LTS runtimes.** Unqualified Node.js or Java means the newest stable release; the stack's
   `versions.md` also names the newest LTS line so a consumer can request it explicitly.

## Component pack

```text
components/<pack-id>/
  README.md          # entry point, at most 200 lines
  changes.md         # what changed across the covered release window
  practices/         # one file per checklist topic: practices/<topic>.md
  anti-patterns.md
  sources.md
  pack.json
  examples/          # project holding every verified block; not delivered to consumers
```

### README.md

Title `# <Name> <line> coding guidelines`, then a header table and four sections:

```markdown
# TypeScript 6 coding guidelines

| Field | Value |
|---|---|
| Component | TypeScript |
| Request | TypeScript 6 |
| Resolved | 6.0.3 |
| Language mode | n/a |
| Targets | none |
| Researched | 2026-10-17 |
| Refresh after | 2027-01-15 |
| Builder | coding-guidelines-builder 2.0.0 |

## How to use this pack

Read this file first. Open the topic file for the task from "Where to look". Check
[changes](changes.md) before relying on remembered APIs.

## Golden rules

### MUST

- <rule, with the reason when it changes a decision> ([types](practices/types.md))

### MUST NOT

- <rule> ([errors](practices/errors.md))

## Most important recent changes

- <what changed and what to do now> ([changes](changes.md))

## Where to look

| Task | File |
|---|---|
| Typing data and APIs | [types](practices/types.md) |
| What changed recently | [changes](changes.md) |
| Reviewing for stale or wrong patterns | [anti-patterns](anti-patterns.md) |
```

- `Resolved`, `Researched` and `Refresh after` equal the `pack.json` values.
- `MUST` and `MUST NOT` hold 1 to 15 rules each; every rule links to the file that explains it.
- "Most important recent changes" holds 1 to 10 items, each linking into `changes.md`.
- "Where to look" links every `practices/` file, `changes.md` and `anti-patterns.md`.

### practices/<topic>.md

One file per topic of the component's checklist (`references/checklists/<kind>.md`), named after the
topic id. A topic that needs more than 400 lines is split into `practices/<topic>-<part>.md` files,
all listed in `pack.json` and routed from the README. Concepts the checklist does not name but the
component needs get their own file under `extra_topics`.

~~~markdown
# Routing: SvelteKit 3

Applies to 3.1.0. Verified 2026-10-17.

## Layouts and route groups

### Put shared UI in `+layout.svelte` and group routes without changing URLs

Layouts nest by directory, and `(group)` directories share a layout without adding a URL
segment, so sections with different chrome need no path prefix. [S4]

<!-- example: src/routes/(app)/+layout.svelte -->
```svelte
...the file's exact content...
```

## Pitfalls

- A `+layout.server.ts` load runs for every child route; see AP-3.
~~~

- One `# ` title, then `Applies to <version>. Verified <YYYY-MM-DD>.` before the first section.
- Every sub-question the checklist lists for the topic is a `## ` section with exactly that title,
  or is listed in the topic's `na_sections` with a reason and a source.
- Every `## ` section except `Pitfalls` holds at least one `### ` recommendation: a short imperative
  title, the reason it is current best practice ("since 6.0" when version-specific) and at least
  one citation.
- `## Pitfalls` is optional and short; it points at anti-patterns.

### changes.md

The covered window is the current major line plus the migration from the previous major. Where
the release line is the minor (Go, Python, Rust, Kotlin, Swift), it is the last four release lines.

```markdown
# TypeScript changes

## 6.0

- **Breaking:** <removed or changed behaviour>; <what to use instead>. [S7]
- **Deprecated:** <API or option>; <replacement>. [S7]
- **New:** <feature worth adopting and when>.
  Continuation lines are indented two spaces. [S8]
```

One `## ` section per release, newest first. Every item starts with `**Breaking:**`, `**New:**`,
`**Deprecated:**` or `**Removed:**`, says what to stop doing and what to do instead, and cites a
source. Old-API snippets here are exempt from example verification.

### anti-patterns.md

~~~markdown
# TypeScript anti-patterns

## AP-1: Numeric enums for string-valued constants

**Category:** Outdated
**Don't:** declare an `enum` for a closed set of strings.
```ts
enum Status { Active, Archived }
```
**Why:** enums emit runtime code that type-stripping tools cannot remove. [S9]
**Do instead:** an `as const` object and a derived union, see [types](practices/types.md).
<!-- example: src/status.ts -->
```ts
...the file's exact content...
```
**Detect:** `grep -nE '^\s*(export )?enum ' -r src`
**Source:** [S9]
~~~

- Entries are `## AP-<n>: <title>` with unique numbers.
- `**Category:**` is `Outdated` (was correct in an earlier release; say which), `Incorrect` (never
  correct) or `Risky` (security, data loss, performance).
- `**Don't:**`, `**Why:**`, `**Do instead:**` and `**Source:**` are required; `**Detect:**` is a
  grep pattern or lint rule when one exists.
- The block right after the `**Don't:**` line is wrong by design and exempt from verification;
  `**Do instead:**` blocks are verified against `examples/`.

### sources.md

```markdown
# Sources

| id | title | url | publisher | version | checked |
|---|---|---|---|---|---|
| S1 | TypeScript 6.0 release notes | https://... | release-notes | 6.0 | 2026-10-17 |
```

`publisher` is one of `official-docs`, `release-notes`, `changelog`, `migration-guide`, `spec`,
`source`, `registry`, `maintainer`, `community`. A community source may corroborate a
recommendation but never be its only source. Every `[S<n>]` citation in the pack resolves here.

### examples/

A minimal project on the pinned toolchain in which every verified block is a file or a marked
region of a file (`references/toolchain.md`). A component that cannot run alone (a UI library
needs a host framework, TypeScript needs a runtime) uses a minimal host, recorded as
`verification.toolchain` with the note "verification host, not a recommendation". Examples stay in
the library; they are not delivered to consumer repositories, so documentation never links into
`examples/`. The block itself carries the code, and the `<!-- example: path -->` marker is only a
comment.

## Stack pack

```text
stacks/<pack-id>/
  README.md          # overview, component table, cross-stack rules, routing; at most 200 lines
  versions.md        # every resolved version, rule applied, compatibility matrix, narrowings, LTS
  decisions.md       # choices for unnamed roles and configuration, with the alternative and why not
  integration/       # one file per seam: integration/<a>-<b>.md
  anti-patterns.md   # seam-level anti-patterns, same format
  sources.md
  pack.json
  examples/          # one project exercising the seams
```

- README title `# <Stack> coding guidelines`, header table with `Stack`, `Request`, `Targets`,
  `Researched`, `Refresh after` and `Builder`, and sections `How to use this pack`, `Components`
  (a table linking every component pack's README with its resolved version), `Golden rules`
  (`MUST` and `MUST NOT` lists including the targets) and `Where to look` (links every seam file,
  `versions.md`, `decisions.md` and `anti-patterns.md`).
- A seam file follows the topic-file rules without a checklist: what each side owns, wiring and
  configuration, the data flow across the boundary, recommendations with citations, pitfalls.
- Stack identity: the user may name the id; otherwise it is the slugs of the framework and runtime
  plus distinguishing components. An existing stack id is reused only when its
  `request_normalized` is identical; otherwise derive a distinct id with a discriminating suffix
  (`-postgres`, `-ts6`). Never overwrite a stack built from a different request.
- Consistency: each edge's `resolved` equals the referenced component pack's `resolved`. Creating
  or refreshing a component pack refreshes every stack that references it in the same run.

## `pack.json`

```json
{
  "schema": 1,
  "id": "typescript-6",
  "type": "component",
  "kind": "language",
  "name": "TypeScript",
  "request": "TypeScript 6",
  "constraint": "6",
  "constraint_source": "compat",
  "narrowed_by": [{"component": "sveltekit-3", "range": "^6.0.0", "source": "S2"}],
  "resolved": "6.0.3",
  "language_mode": null,
  "targets": {},
  "registry": {"type": "npm", "package": "typescript"},
  "researched": "2026-10-17",
  "refresh_after": "2027-01-15",
  "summary": "Strict, current TypeScript 6 practices for application and library code.",
  "load_when": "Writing, reviewing or configuring TypeScript code",
  "topics": {
    "types": {"file": "practices/types.md"},
    "async-concurrency": {"file": "practices/async-concurrency.md",
      "na_sections": [{"section": "Threads and workers", "reason": "Runtime-specific; see the runtime pack", "source": "S3"}]},
    "resources-memory": {"na": "No manual memory management; disposal is covered in errors", "source": "S3"}
  },
  "extra_topics": {},
  "verification": {
    "date": "2026-10-17",
    "toolchain": {"bun": "1.4.3", "typescript": "6.0.3"},
    "toolchain_note": "verification host, not a recommendation",
    "commands": ["bun install --frozen-lockfile", "bun run typecheck", "bun test"],
    "examples_hash": "sha256:...",
    "blocks": {"verified": 41, "exempt_positional": 18, "exempt_explicit": 0},
    "status": "passed",
    "limitations": []
  },
  "review": {"independent": true, "date": "2026-10-17", "open_items": []},
  "builder": {"name": "coding-guidelines-builder", "version": "2.0.0"}
}
```

- `constraint` is the effective constraint or `null`; `constraint_source` is `user`, `compat`
  (needs `narrowed_by`) or `none`.
- Every checklist topic appears under `topics` as `{"file": ...}`, `{"files": [...]}` or
  `{"na": reason, "source": id}`. Every `practices/` file belongs to exactly one topic.
- `refresh_after` defaults to `researched` plus 90 days.
- `verification.examples_hash` is `packs.py hash <pack>` at the time verification ran; the check
  fails when `examples/` changed since. `status` is `passed`, `partial`, `failed` or `not-run`;
  anything but `passed` lists its `limitations`. `blocks` comes from `verify_examples.py --json`.
- `review.independent` is `false` when the review ran in the context that wrote the pack.
- A stack's `pack.json` has `"type": "stack"`, no `kind`, `topics` or `resolved`, and adds
  `request_normalized` (components, constraints, targets and variants such as the database),
  `components` (edges: `id`, `original_request`, `effective_constraint`, `reason`, `resolved`) and
  `integrations` (`{"file": "integration/<seam>.md"}` or `{"na": reason, "source": id}` per seam).

## Rules for every file

- UTF-8 without BOM, LF line endings, no trailing whitespace, exactly one final newline, so a
  consumer's whitespace fixers never rewrite delivered bytes. This includes `examples/`.
- One `# ` title, before any other heading. No empty sections: every heading has content before the
  next heading of the same or higher level.
- Relative links resolve and never point into `examples/`. A component pack links only inside
  itself; a stack pack links only inside itself and to the component packs its `components` edges
  declare. Consumers receive exactly those packs, so any other link would break there.
- Line caps: `README.md` 200, `changes.md` and `anti-patterns.md` 600, `sources.md` none, every
  other file 400. Split by topic instead of trimming.
- No file named `SKILL.md` anywhere in a pack.
